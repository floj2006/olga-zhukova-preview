# Подключение Supabase

После настройки переменных и применения SQL запустите `npm run check:cloud`. Команда проверяет доступ к таблицам без чтения заявок, наличие необходимых RPC-функций и настройки хранилища фотографий. Используются только GET-запросы; данные не изменяются, секреты и тела ответов не выводятся. При недоступной или неполной конфигурации команда завершится с кодом 1.

Эта предварительная проверка не подтверждает актуальность тела SQL-функций, работу записи и правила доступа для публичного клиента. Их необходимо проверить отдельно перед публикацией. `npm run test:cloud-check` проверяет сам скрипт на подставных ответах и не требует облачного проекта.

Проверка Node 24 завершена. Для оставшегося облачного этапа требуется проект в аккаунте владельца сайта.

1. Откройте [Supabase Dashboard](https://supabase.com/dashboard) и создайте проект. Название можно выбрать `olga-zhukova`. Сохраните пароль базы локально.
2. В настройках API получите Project URL и серверный ключ `service_role` (legacy API keys), который ожидает текущий адаптер.
3. В окне **Connect** скопируйте строку Postgres **Session pooler**, подставив пароль базы. Этот вариант подходит и для подключения по IPv4. [Документация подключения](https://supabase.com/docs/guides/database/connecting-to-postgres).
4. Дополните существующий `.env.local`, сохранив текущие настройки администратора:

```dotenv
SUPABASE_URL=https://PROJECT.supabase.co
SUPABASE_SERVICE_ROLE_KEY=SERVER_SERVICE_ROLE_KEY
SUPABASE_DB_URL=POSTGRES_CONNECTION_STRING
SUPABASE_GALLERY_BUCKET=olga-gallery
```

Не отправляйте секреты в чат. Достаточно сообщить, что доступ добавлен. `SUPABASE_DB_URL` нужен для применения SQL, а не для работы публичного сайта.

После появления доступа можно применить `server/schema.sql` и проверить календарь, заявки, поиск, публикацию фотографий и закрытость таблиц для публичного доступа. Альтернатива прямому SQL-подключению — выполнить файл через SQL Editor проекта; [официальное описание SQL Editor](https://supabase.com/docs/guides/database/overview).

Создание облачной схемы не переносит локальные данные автоматически. Существующая `.data` сохраняется; её перенос — отдельная операция с проверкой, какие записи действительно нужно публиковать.

После добавления доступа перезапустите локальный сервер. В админке раскройте «Подготовка к запуску», обновите настройки и запустите «Проверить облачное подключение». Проверка выполняется только чтением; SQL по-прежнему нужно применить отдельно.

После применения схемы доступна дополнительная диагностика server/verify-schema.sql в SQL Editor. Она читает только конфигурацию и проверяет RLS, права таблиц/RPC и стандартный бакет. Все строки должны иметь ok=true. В настоящем облаке этот новый файл пока не исполнен; он не заменяет тест записи в отдельной базе.
